### Главный аргумент: почему FastAPI, а не Django/Flask

- **Django** — слишком тяжёлый для API без шаблонов и админки.
- **Flask** — синхронный по умолчанию, нужно много обвязки.
- **FastAPI** — async, типизация Pydantic, бесплатный Swagger UI на `/docs`, **в 5-10 раз быстрее** Flask по бенчмаркам.

### Почему async везде

При обращении к БД поток не блокируется — пока один запрос ждёт ответ Postgres, сервер обрабатывает другие. Это критично при загрузке больших CSV и запросах с агрегациями.

## 2. Структура проекта

```
backend/
├── app/
│   ├── main.py              # точка входа, middleware, роутеры

│   ├── models/              # SQLAlchemy ORM (таблицы)
│   │   ├── referee.py
│   │   ├── performance.py
│   │   └── assessment.py
│   ├── schemas/             # Pydantic (валидация ввода/вывода)
│   ├── services/            # бизнес-логика
│   │   ├── accuracy.py      # точность судейства
│   │   ├── bias.py          # коэффициент пристрастия
│   │   └── csv_import.py    # импорт CSV
│   └── routers/             # HTTP-эндпоинты
│       ├── upload.py        # POST /api/upload/*
│       ├── competitions.py  # GET  /api/competitions/*
│       ├── categories.py    # GET  /api/categories/{...}
│       └── referees.py      # GET  /api/referees/*
├── tests/                   # 28 тестов, pytest
├── DockerFile               # образ Python 3.11 + uvicorn
├── docker-compose.yml       # backend + Postgres
├── requirements.txt         # фиксированные версии
└── .env                     # секреты, не в git
```

### Архитектурный принцип — **разделение слоёв**

1. **Routers** — только HTTP: парсят URL/тело запроса, вызывают сервис, возвращают JSON
2. **Services** — чистая бизнес-логика, не знают про HTTP. Их легко тестировать
3. **Models** — структура таблиц, отношения
4. **Schemas** — контракт с фронтом (что приходит, что уходит)

> [!tip] Если спросят «зачем такое разделение»
> Чтобы можно было поменять FastAPI на Flask без переписывания бизнес-логики. Тесты сервисов **не требуют HTTP-клиента**.

## 3. Модели данных (зачем нужна каждая таблица)

### `Referee` — судьи
```python
id, fio, region, city
```
Откуда: CSV `referee.csv`. ФИО, регион и город нужны для расчёта **bias coefficient** (свой/чужой).

### `Performance` — выступления спортсменов
```python
id, region, city, competition_type, competition,
age_category, discipline
```
Откуда: CSV `performances.csv`. Содержит метаданные о выступлении — на каком соревновании, чей участник, что выполнял.

### `Assessment` — оценки судей за выступления
```python
id, referee_id (FK), performance_id (FK),
type (EXECUTION/ARTISTIC), number,
referee_assessment,        # что поставил судья
result_type_assessment,    # итоговая по типу (среднее судей)
result_assessment          # итоговая общая
```
Откуда: CSV `assessments.csv`. Связывает судью и выступление — **ядро системы**, по этим данным считаем точность и пристрастие.

### Индексы

На все часто-фильтруемые поля (`competition`, `region`, `referee_id`, `performance_id`, `type`) поставлен `index=True`. Без них запросы `WHERE competition = ...` сканировали бы всю таблицу.

## 4. Бизнес-логика

### 4.1 Точность судейства (`services/accuracy.py`)

**Функция `get_threshold(score)`** — порог отклонения, зависящий от итоговой оценки:
- ≥ 8.0 → 0.3 (для высоких оценок порог жёстче)
- ≥ 7.0 → 0.4
- ≥ 6.0 → 0.5
- иначе → 0.6

**Функция `classify_accuracy()`** — классифицирует оценку:
- `bullseye` — отклонение 0 (точное попадание)
- `acceptable` — отклонение в пределах порога
- `serious` — выходит за порог (грубая ошибка)

**Функция `calc_accuracy_percent()`** — % не-серьёзных ошибок (метрика судьи).

**Функция `calc_exec_art_accuracy()`** — отдельно по EXECUTION и ARTISTIC.

> [!example] Пример для жюри
> Судья поставил `8.2`, итог `8.0`. Порог для `8.0` = `0.3`. Отклонение `0.2 < 0.3` → **acceptable** ✅. Если бы поставил `9.0` — отклонение `1.0 > 0.3` → **serious** ❌.

### 4.2 Коэффициент пристрастия (`services/bias.py`)

Считает, **завышает ли судья своих** (земляков) против чужих:

1. Делит выступления на «свои» и «чужие»:
   - На РФ-соревнованиях: своё = тот же **регион** что у судьи
   - На региональных: своё = тот же **город**
2. Считает **среднее отклонение** в каждой группе
3. `bias = mean_others - mean_own`

**Интерпретация:**
- `bias > 0` — мягче к своим (заниженно к чужим)
- `bias < 0` — строже к своим
- `≈ 0` — нет пристрастия

### 4.3 Импорт CSV (`services/csv_import.py`)

Особенности:
- CSV **без заголовков** (так в исходных файлах от заказчика) → передаём `fieldnames` вручную
- Кодировка `utf-8-sig` — снимает BOM от Excel
- `INSERT ... ON CONFLICT DO NOTHING` — идемпотентность: загрузка одного файла дважды не дублирует записи

## 5. API-эндпоинты

| Метод | URL                                   | Что делает                          |
| -------| ---------------------------------------| -------------------------------------|
| POST  | `/api/upload/referees`                | Загружает CSV судей                 |
| POST  | `/api/upload/performances`            | Загружает CSV выступлений           |
| POST  | `/api/upload/assessments`             | Загружает CSV оценок                |
| GET   | `/api/competitions/`                  | Список соревнований с агрегатами    |
| GET   | `/api/competitions/{name}`            | Детали: судьи, категории, метрики   |
| GET   | `/api/categories/{comp}/{age}/{disc}` | Тепловая карта судья×регион         |
| GET   | `/api/referees/?search=`              | Список судей с метриками            |
| GET   | `/api/referees/{id}`                  | Профиль судьи + история выступлений |

Все эндпоинты защищены валидацией Pydantic. Загрузка CSV — лимит **10 MB** и проверка расширения `.csv`.

## 8. Что отвечать на типовые вопросы

> **«Почему именно FastAPI?»**
> Async + типизация + бесплатный Swagger. Один декоратор `@router.get` и эндпоинт сразу появляется в `/docs` с OpenAPI-схемой. Фронт может генерить TypeScript-типы автоматически.

> **«Почему Postgres, а не MongoDB/SQLite?»**
> Данные **сильно реляционные**: судья ↔ оценка ↔ выступление с FK. SQL-агрегации (GROUP BY, JOIN) гораздо удобнее, чем aggregation pipeline в Mongo. SQLite не подходит для прода — нет concurrent writers.

> **«Зачем Docker?»**
> Чтобы команда не тратила время на установку Postgres, нужной версии Python, asyncpg. `docker-compose up` — и всё работает на любой ОС.

> **«Как масштабируется?»**
> Бэкенд stateless → можно поднять N инстансов за nginx. Postgres — реплики чтения. Async уже оптимизирует один инстанс под высокий I/O.

> **«Что было самым сложным?»**
> Парсинг CSV без заголовков с кодировкой Windows-1251 и формула bias. Решено через `csv.DictReader(fieldnames=...)` и группировку по региону/городу в Python.

> **«Какие тесты?»**
> Юнит-тесты для accuracy/bias (без БД, на dataclass-фейках) + интеграционные через `httpx.AsyncClient` к ASGI-приложению с SQLite в памяти. **28 тестов, 100% покрытие сервисов**.

> **«Что не успели?»**
> Alembic-миграции (сейчас `Base.metadata.create_all`), полноценный response_model на всех эндпоинтах, кеш Redis для часто запрашиваемых соревнований.
